## Notes

- `src/models/use_fans_heatwaves.ts` `use_fans_heatwaves`: the model computes nothing but `two_nodes_gagge`'s kernel, whose arithmetic its register notes (ADR 0009), and exact comparisons of its unrounded outputs, `m_bl == max_skin_blood_flow`, `w == w_max` and `m_rsw == max_sweating`, so each flag is upstream's wherever the kernel's bits are: `max_sweating=100` gives `heat_strain_sweating` 0.0 in both, since the kernel back-calculates an `m_rsw` of 99.99999999999999 (measured on 4.8.0 at `tdb=45, tr=45, v=0.5, rh=30, met=2.0, clo=0.5`). In the parity data (533 rounded cases, 467 unrounded), each of the 4,000 flags equals upstream's, and 11,810 of the 12,000 numeric outputs are bit-identical, the others at most 6.9e-14 relative apart, on Node 26.8.2.
- `src/models/use_fans_heatwaves.ts` `use_fans_heatwaves`: upstream's `np.asarray` calls, `asdict` and its dict comprehensions have no counterpart, since the model takes scalars (ADR 0019, whitelist items 8 and 9): each `_as_flag` call's `valid=~np.isnan(…)` is `!Number.isNaN(…)`, `np.max([…], axis=0)` is `Math.max`, which carries a NaN as `np.max` does, and the `output_vars` comprehensions are loops over the result's keys, which take the dataclass's order, as `UseFansHeatwaves(**output)` does, where `output_vars` puts `heat_strain` last. `two_nodes_gagge` checks the inputs it is given again, as upstream's `GaggeTwoNodesInputs` does, and can throw its "Max iterations exceeded" (deviation two_nodes_gagge-7).
- `src/models/use_fans_heatwaves.ts` `USE_FANS_HEATWAVES_INFO`: `standards` is `[]` (decision 165): the comment "fan_heatwaves applicability limits (extended from ASHRAE 55 baseline)" is prose, and upstream's code calls no standard's check. `rh`'s bounds are written `0` and `100`, as upstream's `_valid_range(rh, (0, 100))` writes them. `max_skin_blood_flow`'s unit, which this model's docstring does not give, is `kg/h/m²`, as `two_nodes_gagge`'s entry for the value it is passed to gives it and as `m_bl`, which it caps, is.
- `src/models/use_fans_heatwaves.ts` `USE_FANS_HEATWAVES_INFO.inputs.position`: `position` references `BASE_INPUTS_POSITION` (`src/_internal/define.ts`), `BaseInputs`' `choice_field` (`classes_input.py:71-73`), with the model's default, 'standing'; `null` passes, as `BaseInputs` skips `None`, and reaches `two_nodes_gagge`, which computes it as standing, as upstream does (measured on 4.7.0: `position=None` gives `e_skin` 63.0, as 'standing' does).
- `src/models/use_fans_heatwaves.ts` `use_fans_heatwaves`: `UseFansHeatwavesInputs` receives neither `max_sweating` nor `round_output` (`classes_input.py:937-966`); `two_nodes_gagge`'s `GaggeTwoNodesInputs` checks `max_sweating` afterwards (`max_sweating="x"` raises its type error on 4.7.0), and nothing checks `round_output` (`round_output="x"` rounds). The parse checks both in `INFO.inputs`' order (deviations _shared-6, _shared-8 and _shared-9).
- `src/models/use_fans_heatwaves.ts` `use_fans_heatwaves`: the `body_surface_area` note's `:py:meth:` reference becomes a code span naming the function (ADR 0025), `body_surface_area`, which the library has in `utilities`, as `two_nodes_gagge`'s does. The rest of the docstring is kept verbatim, the `position` entry, which names two of the three values `choice_field` accepts, the summary's "Ranges from 0 and 1" and the `e_skin` Attributes entry's `e_diff`, which the result does not hold, included (ADR 0025, decision 186); the docstring gives Parameters in another order than the signature's, with `max_sweating` last, and the TSDoc keeps the docstring's, `INFO.inputs` the signature's.
