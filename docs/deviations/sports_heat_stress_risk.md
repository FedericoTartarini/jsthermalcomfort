## Notes

- `src/models/sports_heat_stress_risk.ts` `_phs_scalar`: upstream's `math.exp` in `p_a` is the C library's `exp`, and the kernel's arithmetic, run under numba, is in `phs`'s Notes, where the library's `Math.exp` is V8's own (ADR 0009); `brentq` is the library's port (deviation _shared-45). On the 818 parity cases at or above 23 °C (node v26.8.2, numpy 2.5.4 and scipy 1.18.1 in the parity image), `p_a` equals upstream's on 746, and of the 1,505 thresholds both solve, 1,173 are bit-identical and the others at most 4.9e-15 relative apart; every rounded threshold, risk level and recommendation, and every notice, equals upstream's on all 1,000 cases.
- `src/models/sports_heat_stress_risk.ts` `sports_heat_stress_risk`: upstream's `np.asarray` calls, its `np.vectorize` of `_calc_risk_single_value` and their comments ("Convert to numpy arrays for vectorized calculation", "Vectorize the calculation function to handle arrays" and the line after it) have no counterpart, since the model takes scalars (ADR 0019, whitelist items 8 and 9), and `np.maximum` is `Math.max`. `np.vectorize` with `otypes` calls `_calc_risk_single_value` once per element, so a scalar call warns once per fallback, as the library's call returns one row.
- `src/models/sports_heat_stress_risk.ts` `_PHS_FIXED_INPUTS`: by upstream's comment the values "mirror the values that `phs()` would use" with `acclimatized=100`, `i_mst=0.4` and the 2023 model, so the library reads every other value from `PHS_INFO.inputs`' defaults, which are ISO 7933:2023's (decision 221), one definition of the fact (decision 127), and writes `acclimatized` and `i_mst` as upstream does. The kernel takes its arguments in its positional order (ADR 0019, whitelist item 1), where upstream passes them by keyword.
- `src/models/sports_heat_stress_risk.ts` `_SportsValues`: the dataclass becomes a class whose constructor takes `clo`, `met`, `vr` and `duration` in the dataclass's field order (ADR 0019, whitelist item 1) and runs `__post_init__`'s checks, after setting the fields, as the dataclass does. `_SportsValues` and `Sports` precede `SPORTS_HEAT_STRESS_RISK_INFO`, which references the class, and `_phs_scalar` follows the public function with the other private functions, where upstream defines it before the class (`models/sports_heat_stress_risk.py:48`).
- `src/models/sports_heat_stress_risk.ts` `_calc_risk_single_value`: the `for … else` loops over the two brentq brackets are a `for … of` whose fallback runs when no bracket set the threshold; upstream's `round(…, 1)` is Python's builtin round on Python floats, `pythonRound` (decision 83), and `np.floor` and `min` are `Math.floor` and `Math.min`. Upstream's chained comparisons, `min_t_low <= tdb < t_medium`, are two comparisons joined by `&&`.
- `src/models/sports_heat_stress_risk.ts` `SPORTS_HEAT_STRESS_RISK_INFO`: `SportsHeatStressInputs` types `sport` as a `_SportsValues`, which TypeScript compares by its fields, so it accepts a plain object with them, which the parse rejects, as upstream's `isinstance` does. The parse checks `sport` after the numbers, in `INFO.inputs`' order (deviation _shared-9), where `SportsHeatStressInputs` checks it first (`classes_input.py:1262`); its `rh` and `vr` checks follow the parse in upstream's order, under its comments, and its broadcast check has no counterpart, since the model takes scalars.
- `src/models/sports_heat_stress_risk.ts` `_PHS_IDX_T_CR`: upstream's module constants `_PHS_IDX_T_CR` and `_PHS_IDX_SWEAT_LOSS_G` are exported from the model file, not from an entry point, since upstream's test imports them with `_phs_scalar` and `_calc_risk_single_value` (`tests/test_sports_heat_stress_risk.py:9-16`), as template item 7 allows for those functions.
- `src/models/sports_heat_stress_risk.ts` `Sports`: the docstring's "This class uses a frozen dataclass decorator to prevent modification of the namespace." is kept as upstream writes it, although on 4.7.0 `Sports.RUNNING = 1` and `Sports.RUNNING.clo = 1.0` both succeed; the library's `Sports` cannot be modified (deviation sports_heat_stress_risk-8). [pythermalcomfort#534](https://github.com/pythermalcomfort/pythermalcomfort/issues/534) reports it (decision 250).
