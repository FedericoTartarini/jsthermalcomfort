## Notes

- `src/models/adaptive_en.ts` `adaptive_en`: upstream's arithmetic is numpy's float64 `+`, `-` and `*` on 0-d arrays (`SLOPE * t_running_mean + INTERCEPT`, the bounds `t_cmf - 3.0` to `t_cmf + 4.0 + ce`, `units_converter`'s conversions) and `operative_tmp`'s ISO `np.sqrt`, each correctly rounded and in the library's order, so ADR 0009 has no site here. All 3,066 unrounded finite numeric outputs of the parity data's 1,000 cases are bit-identical to upstream's, and all 2,870 rounded ones equal (node v26.8.2).
- `src/models/adaptive_en.ts` `adaptive_en`: upstream's `np.asarray` calls and its `np.where` on `all_valid` have no counterpart, since the model takes scalars (ADR 0019, whitelist items 8 and 9). `units_converter(tdb=tdb, tr=tr, tmp_running_mean=t_running_mean, v=v)` takes `from_units`' default, IP, which the library's positional call passes explicitly as `Units.IP`. The acceptability is upstream's `_as_flag` of two comparisons, NaN where `t_cmf`, `to` or `ce` is NaN, so it is a nullable `flag`.
- `src/models/adaptive_en.ts` `adaptive_en`: a negative `v` makes `operative_tmp`'s ISO `np.sqrt(10 * v)` NaN, so every acceptability is NaN with a finite `tmp_cmf` upstream (measured on 4.8.0 at `tdb=25, tr=25, t_running_mean=20, v=-0.5`), `null` here (decision 310); numpy's `RuntimeWarning` "invalid value encountered in sqrt" has no counterpart (decision 86). [pythermalcomfort#525](https://github.com/pythermalcomfort/pythermalcomfort/issues/525) reports it.
- `src/models/adaptive_en.ts` `adaptive_en`: the `t_running_mean` note's `:py:meth:` reference to `pythermalcomfort.environment.running_mean_outdoor_temperature` is a code span naming the function (ADR 0025), since the library's `running_mean_outdoor_temperature` is in `environment`, a JavaScript file that no model calls and that is not on the TypeDoc site (ADR 0018). In the `v` note, the `>` that starts upstream's line 48 is written `\>`, which TypeDoc prints as `>`, since a `>` there would open a nested blockquote.
- `src/models/adaptive_en.ts` `ENInputs`: `units` is typed `"SI" | "IP"`, the parse accepts either in any case (decision 172), so the example's comment `units="IP" or "ip" are both valid`, written `units: "IP" or "ip"`, holds at runtime, while a TypeScript caller passing `"ip"` needs a cast. `limit_inputs`, which upstream's `ENInputs` does not receive (`classes_input.py:237-254`), is checked as every switch is (deviation _shared-8).
